# Задания на ЛР 1-4

## Задание

Сделать только 4 ЛР, но соблюсти требования каждой ЛР (некоторые требования уходят на задний план, так что неактуальные для 4 ЛР можно не соблюдать, например, DTO из 1 ЛР).

### Стек

Backend: Java, Spring. Frontend: JS, React.

## Вариант

Облачное хранилище. Сущности: Пользователь -> Папки -> Файлы.

## ЛР 1

Для каждой сущности модели данных json-server (из data.json) разработать DTO и REST-контроллер.
Все поля сущностей должны быть перенесены в DTO. Все поля DTO-класса должны быть приватными.
Класс контроллер должен содержать аннотации @RestController и @RequestMapping. Аннотация @RequestMapping в качестве параметра должна содержать общий префикс для всех контроллеров.
Класс контроллер должен содержать коллекцию объектов DTO-класса. Тип коллекции может быть любой: список (ArrayList), словарь (LinkedMap), и т. д. Переменная для работы с коллекцией должна быть приватной, а заполнение предопределенными данными должно выполняться в конструкторе.
Класс-контроллер должен содержать стандартные CRUD-операции: create, read, update, delete.
Работу контроллера следует проверить через интерфейс Swagger (Swagger UI).
React-приложение также должно работать с полученным REST API.

## ЛР 2

Для каждой сущности создать класс для описания модели данных. Класс-сущность должен наследоваться от класса BaseEntity, содержать конструктор по умолчанию, конструктор с аргументами для создания объектов вручную, геттеры и сеттеры для полей класса. Если сущность имеет связь с другой сущностью на уровне внешних ключей, то такую связь необходимо реализовать на уровне ссылок (поле класса как переменная или коллекция с соответствующим типом).
Для работы с каждой сущностью требуется создать репозиторий. Каждый репозиторий должен являться наследником класса MapRepository и реализовывать интерфейс CommonRepository.
Для каждой сущности создать сервисный класс с реализацией соответствующей бизнес-логики. Класс с бизнес-логикой должен использовать в качестве зависимости репозиторий. Класс для работы с бизнес-логикой должен содержать публичные методы для реализации функций CRUD и использовать репозиторий для работы с хранилищем. 
Для каждой сущности необходимо реализовать контроллер. Контроллер должен использовать в качестве зависимости сервисный класс. Контроллер должен содержать все необходимые CRUD-методы. При выполнении метода контроллера должен вызываться соответствующий метод из класса с бизнес-логикой. На уровне контроллера необходимо реализовать контроль корректности данных в DTO (validation). Также требуется разработка компонентов для преобразования объекта класса-сущности в DTO и обратно (mapping).
Каждый контроллер должен работать с отдельными DTO для запроса (Rq) и ответа (Rs). CRUD-методы сервисного класса должны использовать Rq DTO в качестве аргументов, а Rs DTO в качестве типа возвращаемого значения. 
Корректность работы приложения следует проверять с помощью модульных тестов. Необходимо создать отдельный класс с тестами для каждой сущности. См. пример.
В приложении следует использовать соответствующие аннотации для создания компонентов. Работа с компонентами должны быть реализована на основе принципов инверсии управления с помощью внедрения зависимостей через конструктор.
Адаптировать клиентское приложения для работы с серверным приложением.

## ЛР 3

Для выполнения ЛР 3 необходимо взять код ЛР 2.
Добавить в качестве зависимостей проекта модуль Spring Data и драйвер для работы с СУБД H2.
Внести настройки для Spring Data и H2 в файлы application.properties для приложения и тестов.
Каждую сущность проекта необходимо снабдить аннотацией @Entity для включения ее в контекст постоянства. Необходимо настроить отображение связей между сущностями.
Наличие двунаправленной связи является обязательным для данной работы, в следующих работах эту связь можно заменить на однонаправленную или удалить. Для двунаправленной связи необходимо использовать getterы и setterы, которые связывают экземпляры сущностей на уровне ссылок.
Все репозитории сделать интерфейсами и наследовать их от интерфейса CrudRepository или JpaRepository для смены типа хранилища с ОЗУ на БД.
В репозитории также следует добавить методы для выполнения запросов к БД для реализации отчетов и/или вывода статистики. Функции отчетов следует продумать отдельно, но для их реализации обязательно следует использовать фильтрацию, группировку и функции агрегации.
В качестве типа результата отдельных методов репозиториев необходимо использовать проекции.
Все публичные методы сервисов следует снабдить аннотацией @Transactional для их выполнения в рамках транзакций.
Корректность работы приложения следует проверять с помощью модульных тестов. Необходимо создать отдельный класс с тестами для каждого публичного метода каждого сервисного класса.

## ЛР 4

Для выполнения ЛР 4 необходимо взять код ЛР 3.
Реализовать поддержку пагинации для одного или нескольких REST-контроллеров. Пагинация в react-приложении также должна быть реализована.
Добавить в приложение поддержку профилей dev, prod и front на уровне конфигурационных файлов для приложения и тестов, а также на уровне gradle. В рамках профилей dev и prod должны использоваться разные СУБД.
Добавить возможность сборки react-приложения и серверной части приложения в единый jar-файл.React-приложение должно быть собрано только при использовании профиля front. Для корректной работы react-приложения следует создать специальный контроллер для перенаправления запросов от сервера к клиенту для выполнения spa-маршрутизации.
Добавить в приложение возможность работы с механизмом версионной миграции. Необходимо реализовать несколько изменений (changelog). Продемонстрировать умение работать с задачами gradle для автоматизации работы с миграциями: создание модели данных на основе существующих изменений, откат изменений, автоматическое формирование изменений, проверка статуса миграции.
В рамках сдачи ЛР следует продемонстрировать умение формировать изменения вручную для вновь созданной сущности с последующей проверкой работоспособности приложения.
